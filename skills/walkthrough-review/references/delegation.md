# 担当分担とコンテキストの節約

サブエージェントが利用可能かつ環境の指示で許可され、独立した範囲へ分ける効果がある場合に使う。
小さいレビューや依存関係の強い一続きの処理は親が担当する。利用できなくても同じ作業をファイル単位で順に進める。
総トークン使用量が必ず減るとは限らない。親に全文・全JSONを返さず、別々の文脈で担当範囲に集中することが目的である。

## 分担の単位

保存はカード単位、分担は関連ファイル・責務単位にする。カード1枚ごとにエージェントを起動しない。
親が対象選定とbuildを済ませ、共通の固定スナップショットと一つのカードストアを用意してから委任する。
各担当へ対象一覧、必要な設計上の前提、CLIとストアの絶対パス、担当名・IDの接頭辞、完了条件を渡す。
環境が対応していれば、親の会話履歴全体を継承せず、必要な参照だけを独立コンテキストへ渡す。
モデルや同時数を固定せず、環境の上限と対象の規模に合わせる。追加のAPIキーや外部サービスを前提にしない。

本ツールを対象とする場合の分担例：

| 担当 | 対象として選ばれたファイル | 主な説明 |
| --- | --- | --- |
| Python担当 | walkthrough.py、diff_parser.py、prepare_review.py | 取込・差分・入力検証・失敗時の扱い |
| UI担当 | app.js、style.css、HTMLテンプレート | 表示・行参照・カード操作・スクロール |
| テスト担当 | 対象に含めたテスト | 何を保証し、何は検証していないか |
| 親 | 概要と全体統合 | 入口からの流れ、担当間の接続、対象漏れ・説明の矛盾 |

これは例であり、常に四役を作る要件ではない。巨大な単一ファイルを分担する場合は、
担当範囲と共通する前提を先に整理し、ファイル全体の整合を確認する担当を一人置く。

## サブエージェントへの依頼例

```text
担当はPython実装です。対象は指定した2ファイルです。
固定スナップショット: <REVIEWの絶対パス>
カードストア: <STOREの絶対パス>
カードCLI: <comment_cards.pyの絶対パス>
手順: <card-authoring.mdの絶対パス>
担当名はpython、新規カードIDはpython-で始めてください。

readで各対象の全文を必要に応じて分割して確認し、責務・保証・失敗時の挙動を説明してください。
旧新が異なる場合は両版を確認し、必要な図はSVG規約を読んで添えてください。
カードはadd/updateで1件ずつ保存してください。共有のreview.json、概要、comments.jsonは編集しないでください。
担当外のコードとの接続は参照で示し、不明点や他担当へ確認が必要な点を報告してください。

全カード・図・該当コードを自己確認し、修正後に担当ファイルへreviewedを付けてください。
完了報告は、確認したファイル、カードの担当名とID、未解決事項、保存先を短く記載してください。
カード本文・コード全文・全JSONは返さないでください。
```

## 親の統合確認

- 各担当の完了を待ち、報告と `status` を照合する。未担当・未確認の対象を残さない。
- ファイル間の呼出し・データの流れ・保証の接続を確認し、説明の重複や矛盾を必要なカードだけ取得して解消する。
- 概要を作成し、不要と判断したカードの理由、対象外、走査警告、未実施の検証を反映する。
- 最終export/merge後のHash・行参照・図・説明を確認する。確認後に修正したカードは担当へ再確認させる。
- 同じ対象・パッチで最終buildを実行し、コード変更があれば新しいストアへ引き継ぎ、影響した説明を再確認する。
- 概要・コード・解説・内部リンク・図をブラウザーで確認し、完成条件を満たした資料を渡す。

機械検証は意味の正しさや説明漏れを判定しない。全対象の全文と全カードの確認は担当全体で行い、
親が全コード・全カードを同じ会話へ再読して分担の効果を失わないようにする。
独立した再レビューが有益な複雑な箇所は、元の結論を与えず別担当にコードと成果物を確認してもらう。
