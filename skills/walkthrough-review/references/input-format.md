# 入力形式・解説・ハッシュ

通常は [カード作成ツール](card-authoring.md) が以下のJSONを集約する。LLMはカードの本文Markdown・任意のSVGと小さなメタ情報を1件ずつ渡し、全配列を生成しない。以下は検証・直接API利用のための形式説明である。どのJSONもUTF-8、パスはプロジェクト相対・`/`区切り。

```json
{
  "overview": "# 注文処理\n入口、責務、データの流れ、レビュー対象と対象外の理由。",
  "comments": [
    {
      "id": "discount",
      "file": "src/main.py",
      "start_line": 4,
      "end_line": 9,
      "side": "new",
      "code_hash": "ここをreview.jsonの該当ファイルのcode_hashes.newの値に置き換える",
      "title": "割引適用と下限の保証",
      "body": "何を保証するか、なぜここで行うか、他の処理に何を渡すかを説明する。[合計の検証](review:src/pricing.py#L1)と責務を分ける。"
    }
  ]
}
```

上は形式説明。実際の行番号・リンク・ハッシュは生成済みデータで確定し、説明文をハッシュに入れない。

- `id` は英数字で始まる1〜64文字の英数字・ハイフン・下線。全コメントで一意。
- 行範囲は両端を含む。通常・変更後は `side: "new"`（省略可）、旧行は `side: "old"`。
- 各カードでは境界条件、例外、呼び出し関係、判断が必要な設計を実装と結び付ける。実装から分かる動作と推測した意図を分ける。
- `code_hash` は解説を作成・確認した版の `code_hashes[side]`。通常はカードツールが固定スナップショットから記録し、LLMは転記しない。直接JSONを作るAPI利用時も、確認した版の値を使う。元バイト列の `sha256` とは異なる。
- リンクは `[説明](review:src/pricing.py#L1)`。旧行は `#O1`。空白等のパス文字はURLエンコードする。対象に含めたファイルの実在行だけをリンク先にする。
- 任意の `diagrams` 配列に `{ "title": "...", "description": "...", "svg": "<svg ...>...</svg>" }` を追加できる。図が不要なら省略するか空配列にする。図の形式と作成方法は [SVG図の作成規約](svg-diagrams.md) を参照する。
- `merge` は概要と全コメントを置き換える。通常は個別修正をカードストアへ保存し、`export` が残す全カードを集約してからマージする。1カードだけのJSONを直接 `merge` へ渡さない。

生成済み `review.json` の本文は `files[].blocks` に保存される。同じ区分で連続する行をまとめた `text` と、旧新の開始行番号 `old_start` / `new_start` を読む。本文のLFごとに行番号が1増える。ファイル全体の `text` や行配列 `rows` は保存しない。旧新それぞれの全文・番号は `self-review.md` でも確認できる。

## 再生成したとき

同じ出力先の `build` は図を含む旧解説を保持し、新しいコードと照合する。`merge` は保存済み `review.json` を使い、元プロジェクトを再走査しない。

| 状態 | 意味と対応 |
| --- | --- |
| `hash_status: verified` | 記録したハッシュと取り込んだコードが一致 |
| `hash_status: mismatch` | コードが異なる。本文・図・行・意図を読み直して修正後にハッシュを記録 |
| `hash_status: missing` | ハッシュ未記録。コードと説明を確認して記録 |
| `range_status: missing` | 参照範囲が消失。近くの行へ自動で付け替えず、新しい対応を確認 |
| `unattached_comments` | 対象から外れたファイルの旧解説。対象範囲を見直し、残す全解説を再マージ |

`hash_warnings` と `self-review.md` を確認する。不一致・未記録でも出力されるため、コマンド成功だけで完了にしない。再ビルド時の概要・本文のリンク切れも確認する。

ハッシュ対象はUTF-8のBOM除去・LF統一後の全文で、末尾改行の有無を保持する。独自計算や推測は不要。図は所属カードと同じ行範囲・版・作成時ハッシュに対応させる。ハッシュ一致は解説や図の意味、作成者の真正性を保証しない。ファイル権限や名前変更などの `diff_summary` は本文ハッシュとは別に確認する。

静的HTMLは元プロジェクトを監視しない。コードの更新検出には `build` が必要。ブラウザーの再読み込みや `merge` だけでは更新を検出できない。
